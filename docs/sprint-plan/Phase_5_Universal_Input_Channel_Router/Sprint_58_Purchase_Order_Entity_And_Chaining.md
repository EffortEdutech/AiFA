# Sprint 58 — Draft-and-Approve Bridge I: Sales & Purchases

**Duration:** Weeks 11-12 (of Phase 5)
**Architecture references:** Vol_5_5 §7 (PO as a Vol 6_2 extension), §9 (the chaining rule this sprint proves live, unchanged from the original design); Vol 6_2 (Purchase Operations — extended, not created fresh); `paymentVouchersReportsTransport.ts` (the draft→approve→post pattern this sprint generalizes to Sales)

**CORRECTION (14 September 2026, made before any revised Sprint 58 code was written):** This sprint slot originally held "Purchase Order Entity & Post-Approval Chaining," scoped narrowly to PO because the pre-revision plan named "any domain beyond leave_application and purchase_order" as out of scope for the whole phase. The owner's 14 September 2026 objective statement removed that exclusion (see `00_Sprint_Plan_Overview.md`'s own scope-revision note). Rather than leave Purchase Orders as an isolated one-off bridge while Sales has none at all, this sprint is widened to cover both Purchases (the original PO scope, fully retained below, unchanged in design) and Sales (`sale` domain: a captured invoice/receipt/quotation-style description becomes a real Quotation/Invoice draft) — grouped together because both are document-cycle domains that already have a working manual multi-step module (`quotationInvoiceTransport.ts` for Sales, the PO schema below for Purchases) for the AI-drafted version to feed into.

---

## Theme

The first of three domain-bridge sprints (58-60) applying the same proven shape — AI classifies and extracts, a draft row is created, the existing approval engine decides, an approved draft either posts or chains to the next real step — to two more of the owner's ~14 domains. Purchases (PO) remains the heaviest single piece of new schema in this phase, exactly as before; Sales is new to this sprint and reuses machinery that already exists and works (`quotationInvoiceTransport.ts`), so no new document-cycle design is needed there, only a drafting entry point into it.

## Objectives

A forwarded or captured Purchase Order becomes a real multi-line document with its own status lifecycle; once approved, it automatically chains to a stock-receipt-pending intake, then a payment-due intake, without the owner re-typing anything the PO already stated (unchanged from the original design). Separately, a forwarded or typed sale description ("invoiced ABC Sdn Bhd RM500", a photographed sales receipt) becomes a real Quotation or Invoice **draft** the owner reviews and confirms before it is sent to a customer or affects AR — never an auto-created, already-issued document, since issuing a document to a real customer is a materially bigger action than recording an internal expense.

**CORRECTION #3 (14 September 2026, found while scaffolding, before schema code was written):** Three things checked directly against `00000000000000_initial_schema.sql` and `quotationInvoiceTransport.ts` changed this sprint's actual remaining work:

1. **The Sales "new RPC" already exists.** `public.create_quotation` (and its transport wrapper `createQuotation`) already accepts `p_ai_draft_summary`/`p_auto_approved` and already routes through `create_approval_task` exactly as this sprint describes — it was built in Sprint 28, before Sprint 57/58 existed, for a human filling the form manually. There is no new `create_draft_quotation_or_invoice` RPC to write; the real remaining Sales work is wiring an AI-classified `sale` capture to *call* the existing `create_quotation` with `autoApproved: false` always, plus item 2 below.
2. **No party-name-resolution function exists anywhere in this schema.** `create_quotation` requires an existing `party_id` and raises `party_not_found_for_this_business` otherwise; `create_party` exists but nothing resolves a bare counterparty *name* (which is all Sprint 57's classifier extracts) to a party row, or creates one if missing. Both Sales and Purchases need this, so it is added once, shared, below (`find_or_create_party`) — a genuine small addition, not scope creep.
3. **There is no `'purchases'` capability domain, and adding one is bigger than this sprint's additive-only promise.** `caller_has_capability`'s domain is a fixed, explicitly "never owner-editable" catalog of 11 values (`sales, pricing, expense, inventory, accounting_reports, tax_compliance, payroll, hr_attendance_leave, commission, legal_contract, settings`) — the same literal array is duplicated across three separate `check` constraints (`permissions`, `segregation_of_duties_policies`, `approval_tasks`). Adding a 12th domain means altering all three constraints, seeding new permission rows, and deciding what every existing role template grants for it — a cross-cutting change well beyond "new tables + one RPC," and not something to do silently while scaffolding. This schema's own precedent already answers the question anyway: `create_party` gates a `supplier` party under `sales` capture, not a dedicated purchases domain, and `expense` is the existing money-out capture domain. `purchase_order` capture/view below uses `'expense'`, matching that precedent — kept additive, no constraint changes. If the owner later wants PO segregated from Expense for approval routing/SoD purposes, that is its own small follow-up, not silently decided here.

## Task Breakdown

### Shared — counterparty resolution (new, not in the original task breakdown)
- New `find_or_create_party(business_id, display_name, party_types)` RPC: case-insensitive lookup by `display_name` within the business; creates a new `parties` row (via the same numbering `create_party` already uses) only if no match exists. Gated identically to `create_party` today (`sales` capture for `customer`/`supplier`/`agent`/`dropship_partner`, `hr_attendance_leave` capture for `employee`) — no new capability surface introduced
- Exposed as `findOrCreateParty` in `partyAndLedgerTransport.ts`, alongside the existing `createParty`

### Purchases — Purchase Order entity & chaining (unchanged from original Sprint 58 design)
- New `purchase_order` and `purchase_order_line` tables (business-scoped, RLS matching the pattern every other business-owned table in `00000000000000_initial_schema.sql` already uses) — status lifecycle: `drafted → approved → stock_received (partial or full) → paid → closed`
- `create_purchase_order` RPC (SECURITY DEFINER, matching every other mutating RPC's convention) accepting AI-extracted line items from Sprint 57's classifier
- A classified `purchase_order` routes to `create_purchase_order`, not a ledger post directly (a PO is never itself a ledger entry — it becomes one only once paid, exactly like Quotation → Invoice → Payment)
- Route a drafted PO through the existing `create_approval_task` engine; on approval, construct a new intake tagged `stock_receipt_pending` carrying the approved PO's line items forward, re-entering the same router every other domain uses (Vol_5_5 §9); on full stock receipt, construct the next intake (`payment_due`) the same way

### Sales — Quotation/Invoice draft entry point (new this revision)
- New `create_draft_quotation_or_invoice` RPC-facing function in `quotationInvoiceTransport.ts` (or an additive wrapper around its existing create calls) that accepts a classified `sale` domain's extracted fields (counterparty, line items or amount, a stated document type if extractable, defaulting to Quotation when ambiguous — never defaulting to an already-sent Invoice) and creates a real `drafted`-status Quotation/Invoice row, reusing the existing document schema and numbering, not a parallel structure
- Route a drafted sale document through the existing `create_approval_task` engine exactly like a Payment Voucher does — approval here means "the owner confirms this is correct and ready," not a second business-level sign-off beyond what Quotations/Invoices already require today
- On approval, the draft becomes a normal Quotation/Invoice indistinguishable from one entered manually — no new status values are introduced into `quotationInvoiceTransport.ts`'s existing lifecycle beyond the `drafted` origin flag needed to know it came from AI capture

## Dependencies

## Risks

| Risk | Mitigation |
|---|---|
| This remains the heaviest single sprint in the phase (new PO schema plus a new Sales entry point) and risks becoming two sprints' worth of work under one number | Scope explicitly to ONE PO chain (PO → stock-receipt-pending → payment-due) and ONE Sales entry point (draft creation only, reusing all existing document logic) — no partial-line receiving, no PO amendment, no AI-driven document *sending* (the owner still sends a Quotation/Invoice the same way they do today) |
| Defaulting an ambiguous captured sale to "Quotation" rather than "Invoice" could itself be wrong in the other direction for some owners | Both are drafts requiring explicit owner confirmation before anything is sent to a customer, so a wrong default costs one extra click, never a wrongly-issued document |
| Chaining logic (Vol_5_5 §9) is new and unproven outside the PO example — a design flaw here would be expensive to unwind once Sprint 59/60 domains start relying on the same pattern | Treat this sprint's chaining implementation as the FIRST proof of the pattern, not the final generalised form, exactly as the original Sprint 58 stated; Sprint 61 is where it is deliberately generalized only after this proof exists |

## Safe to Carry Over

Partial-line stock receipt, PO amendment after approval, multi-supplier consolidation, AI-assisted document sending/delivery for Sales, and Credit Note drafting from a captured return/refund description — genuinely out of this sprint's one-chain-per-module-group scope, logged as open items for a future Purchase Operations or Sales deepening pass.
