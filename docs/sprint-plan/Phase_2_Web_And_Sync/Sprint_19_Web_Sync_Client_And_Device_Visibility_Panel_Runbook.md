# Sprint 19 — Web Sync Client & Device Visibility Panel Runbook

**Purpose:** documents the `@aifa/core/sync/supabaseTransport.ts` extraction, the web sync client built on top of it, the full cross-platform Devices panel (Vol 12_1 §8), and two real, disclosed gotchas found and resolved along the way — a build-time cross-package typing collision, and a Sprint 18 persistence design that turned out to be incompatible with what sync actually needs.

**Companion documents:** `Sprint_19_Web_Sync_Client_And_Device_Visibility_Panel.md` (this sprint's task breakdown), Vol 12_1 §5a/6/6a/8 (device registry, sync protocol, handoff, device visibility), Sprint 18's own runbook (the web app shell this sprint builds sync onto).

---

## 1. What was built

**`packages/core/src/sync/supabaseTransport.ts`** (new) — the Supabase-specific `SyncTransport` implementation, previously hardcoded inside `app/src/db/syncService.ts` and bound to mobile's own `supabase` client import, moved into `@aifa/core` and parameterised by an injected client (`createSupabaseSyncTransport(client)`). A new `createSupabaseDevicesTransport(client)` covers every device-registry RPC/query: `registerDevice`, `renameDevice`, `revokeDevice`, `requestActivation`, `requestPrimaryTakeover`, `setPrimaryDevice`, `touchDeviceHeartbeat`, `getRegisteredDevices` (revoked-filtered, for action-target pickers), `getAllDevices` (new this sprint — every non-deleted device including revoked, for the Devices panel listing itself), `getActiveDeviceInfo`, `getMaxServerSeq`. This directly satisfies the sprint's own Task Breakdown ("should mostly be reuse through @aifa/core, not a parallel implementation") and its risk register's concern about mobile/web inventing inconsistent device label/platform strings independently.

**`app/src/db/syncService.ts`** (refactored) — now imports the shared transports instead of defining them locally. Every existing exported function name/signature is unchanged (zero call-site changes needed elsewhere in `app/`). New exports: `renameDevice`, `revokeDevice`, `getAllDevices`, `getMaxServerSeq`, `getLocalSyncCheckpoint`.

**`web/src/lib/syncService.ts`** (new) — the web counterpart, built the same way: thin, web-specific glue constructing the shared transports against web's own `supabase` client. The one structural difference from mobile's file: every function takes `db: SqlDb` as an explicit parameter rather than calling a module-level `getDb()` singleton, because web has no such singleton — `App.tsx` holds the one open `SqlDb` in React state and threads it through props, and this file follows that existing convention rather than introducing a new one.

**`web/src/hooks/useWebSync.ts`** (new) — one consolidated hook standing in for mobile's three separate hooks (`useSyncResume.ts`, `useDemotionPoll.ts`, `useActiveDeviceInfo.ts`): a sync cycle on mount and on every `online` browser event, a 30s foreground-only (`document.visibilityState === "visible"`) poll refreshing the active-device lock, and the live `ActiveDeviceInfo` the banner needs. Consolidated into one file deliberately — web's `App.tsx` is a single small root component (unlike mobile's `App.tsx` + `AppNavigator` split), and three separate hook files would have been more ceremony than the smaller app warrants. Behaviour matches mobile's three hooks combined.

**`web/src/components/ReadOnlyBanner.tsx`** (new) — the web counterpart to mobile's `ReadOnlyBanner.tsx`. Same handoff decision logic (`resolveActivationConfirmation`/`describeReadOnlyReason` from `@aifa/core/sync/handoff`, unchanged, shared verbatim); `window.confirm` instead of React Native's `Alert.alert` for the confirmation prompt, since no modal component exists anywhere in `web/` yet and building one was a bigger investment than this one confirmation dialog needed. Wired into `App.tsx` above the tab bar.

**`app/src/components/DevicesPanel.tsx`** and **`web/src/components/DevicesPanel.tsx`** (new, replacing Sprint 17's minimal `PrimaryDeviceSettingsCard.tsx` on mobile) — the full Vol 12_1 §8 panel on both platforms: Device label, Platform, Status (Active/Read-only/Revoked, derived), Primary badge, Sync state ("Up to date"/"N changes behind"/"Never synced"), Last seen, Registered, and all four actions (Make this device active, Set as primary, Rename, Revoke). Wired into mobile's `SettingsScreen.tsx` and web's `SettingsReadOnly.tsx` respectively.

**`app/backend/schema.sql`** — two new RPCs, `rename_device` and `revoke_device` (see §3 below for the design reasoning on `revoke_device`'s replacement-device handling).

**`app/backend/verification/sprint19_cross_platform_consistency_test.py`** (new) — extends Sprint 15's simulated-Postgres/psycopg2 harness pattern: two independent RPC-calling sessions, standing in for "mobile" and "web" (both reduce to RPC/query callers at the protocol level), proving a device registered/renamed/revoked via one session is immediately, correctly visible from the other, and that a revoked device can never again pass a `revoked_at is null` RPC guard from either session. 8/8 checks pass — see §5.

## 2. Design decision: `Devices` panel columns, and what "Make active" means per row

Vol 12_1 §8's table says the panel "lists every non-deleted row in `public.devices`". The existing `getRegisteredDevices` query (used since Sprint 17 for primary-reassignment/activation-target pickers) filters `revoked_at is null` — correct for a picker (you can never select a revoked device as a replacement), wrong for the panel's own listing (a revoked device should still appear, with Status = Revoked). Rather than changing `getRegisteredDevices`'s existing, already-relied-upon semantics, this sprint added a second query, `getAllDevices`, with no such filter — the panel uses `getAllDevices`; every action-target picker (set-primary, activate, revoke's own replacement-device arguments) keeps using `getRegisteredDevices`.

"Make this device active" is shown on exactly one row: the one representing the device the owner is currently looking at the panel FROM. Vol 12_1 §6a.1 is explicit that a device can only ever request activation for itself — there is no RPC that lets one device push another one active — so showing that button on every row would promise something the protocol doesn't support. Both platforms' panels reuse the exact same activation flow their existing `ReadOnlyBanner` already implements (`resolveActivationConfirmation` + `requestActivation`/`requestPrimaryTakeover`) rather than inventing a second one.

"Set as primary" and "Rename" are available on any non-revoked row — both are pure administrative reassignments the owner can make from wherever they're looking at the panel, consistent with Sprint 17's `PrimaryDeviceSettingsCard` already assuming this for primary reassignment.

"Revoke" auto-selects a replacement active/primary device (defaulting to the current primary, falling back to any other remaining non-revoked device) rather than presenting a second picker UI — Vol 12_1 §8's own text only requires "defaulting to the primary device if one exists," which this covers; a full "choose your own replacement" picker is a real UI investment this sprint didn't spend building. If revoking the last remaining non-revoked device (no valid replacement exists), Revoke is disabled client-side with an explanatory message rather than attempting an RPC call that would fail anyway.

## 3. Design decision: `revoke_device`'s three required behaviours, and the one NOT implemented

Vol 12_1 §8 describes three things a revoke must do: (1) set `revoked_at`, (2) force-sign-out that device's Supabase session, (3) if the revoked device was active, require the owner to immediately activate a replacement (defaulting to primary).

**(1) and (3) are implemented**, exactly as described, with two backend-enforced guardrails not explicit in Vol 12_1's prose but decided here as the conservative reading: if the device being revoked currently holds the active lock, the caller MUST supply a replacement (`must_designate_replacement_active_device` otherwise — never a silently-orphaned lock); if the device being revoked is currently primary, the caller MUST similarly supply a new primary (`must_designate_new_primary_device` — Vol 12_1 §8's text doesn't explicitly say what happens to primary status on revocation, so this project never silently leaves a business with zero primary device).

**(2) is NOT implemented — a real, disclosed gap, not a silent omission.** This app's auth model is one Supabase user (`auth.uid()`) per **business**, shared identically across every device that business has ever registered — there is no per-device Supabase session to selectively invalidate without a new layer of session-to-device tracking this schema does not have. A SECURITY DEFINER function deleting rows from Supabase's own internal `auth.sessions`/`auth.refresh_tokens` tables was considered and rejected: those are undocumented internals of a vendor-managed schema, not a stable contract this project should depend on — the same reasoning that has kept this codebase away from other undocumented-internals dependencies throughout (e.g. `@noble/*` over ad-hoc crypto). This was a judgment call, not put to the owner via `AskUserQuestion` — there wasn't a real engineering alternative to weigh (the only alternative was strictly worse/riskier), so the decision was disclosure, not a choice needing the owner's input.

What IS guaranteed, immediately and unconditionally, the same way every other RPC in `schema.sql` already works: a revoked `device_id` can never again pass the `revoked_at is null` check in `request_activation`, `request_primary_takeover`, `set_primary_device`, or `touch_device_heartbeat` — so it can never become or remain the writer, full stop, regardless of what its still-valid Supabase session can still technically call against non-write-gated endpoints. Full decrypt-level revocation still needs DEK rotation — the same top-priority open item Vol 12_1 §12 already names, framed here the same way, not a new gap this sprint introduced. Verified directly in §5's cross-platform script (Step 7).

## 4. Two real build-time gotchas found and fixed this sprint

**Gotcha 1 — cross-package `SupabaseClient` type collision.** `packages/core` has no `dependencies` field of its own (established precedent — `@noble/hashes`/`@noble/ciphers` aren't listed there either despite being genuinely imported), and this monorepo has no workspace-level dependency hoisting, so `app/` and `web/` each install their OWN separate copy of `@supabase/supabase-js`. Both are the same published version, but `SupabaseClient` (and the postgrest query-builder classes it returns) carry protected members, which makes TypeScript treat two separately-installed-but-structurally-identical copies as INCOMPATIBLE types — a real `tsc` failure the moment `createSupabaseSyncTransport`/`createSupabaseDevicesTransport` were typed against the imported `SupabaseClient` class directly. Fixed by replacing that import with a small, hand-written `SupabaseClientLike` interface covering only the two methods this file actually calls (`.rpc`, `.from`) — genuine structural/duck typing, so it accepts either installed copy identically. Trade-off, disclosed rather than absorbed: `.from()`'s query-builder chain is typed `any` inside `supabaseTransport.ts`; the existing `as DeviceRow`/`as SyncEnvelopeRow` casts at each call site (already present, unchanged) are what keeps the mapped output typed, not the chain syntax itself. Confirmed fixed: both `app/`'s and `web/`'s `tsc --noEmit` are clean against the shared file.

**Gotcha 2 — Sprint 18's web key-persistence design was incompatible with what sync needs.** Sprint 18 deliberately persisted the imported *non-extractable CryptoKey object* (via IndexedDB structured-clone), discarding the raw DEK bytes immediately after import — explicitly framed then as the stronger, WebCrypto-native choice. Sprint 19's sync client broke that: `@aifa/core`'s shared envelope crypto (`dek.ts`) is built on `@noble/ciphers`, which has no concept of a CryptoKey and requires a plain `Uint8Array` DEK for every push/pull cycle — the same shape mobile's `syncService.ts` already passes it. Reworking `@aifa/core`'s already-shipped, already-tested envelope crypto to accept a WebCrypto `CryptoKey` instead, for one platform's storage preference, would have been a far larger and riskier change than revising web's own key-persistence choice. Resolution: `keyStore.ts` now persists the owner's **recovery code** instead of a CryptoKey (still IndexedDB, never localStorage/sessionStorage) — exactly mirroring mobile's own pattern (`app/src/db/client.ts`'s `storeSyncRecoveryCode`/`getStoredSyncRecoveryCode` via Expo SecureStore). The raw DEK is re-derived fresh each session from the persisted code via `deriveBusinessDek`, held only in memory for that session, never itself written to browser storage. `deviceBootstrap.ts` derives a non-extractable CryptoKey from those same in-memory bytes, each session, purely for `sqlJsAdapter.ts`'s separate whole-DB-image encryption — that CryptoKey is now never persisted at all (Sprint 18's structured-clone trick is retired). What actually differs from Sprint 18's original design, stated plainly: WHICH secret sits in browser storage — the recovery code, not raw key bytes, not a passable-around key object. Vol 12_0 §6's own text ("no OS keychain... explicitly weaker-than-mobile") already frames browser storage as the least-bad option on this platform; a recovery code in IndexedDB is that same already-accepted risk class, not a new, worse one — it's the identical value the owner already typed into `DeviceSetupScreen`, and the same value mobile's SecureStore already treats as storable (with a stronger OS-level guarantee mobile gets and web structurally cannot).

## 5. Verification performed this sprint

- **Mobile regression, twice** (after the `syncService.ts` refactor, and again after the `DevicesPanel.tsx` wiring): `npx tsc --noEmit` clean both times; full Jest suite (`node --experimental-sqlite node_modules/.bin/jest`) — **19/19 suites, 165/165 tests, unchanged from Sprint 17/18's baseline** both times, confirming zero behavioural regression from the shared-transport extraction.
- **Web**: `npx tsc --noEmit` clean; `npx eslint src verification --ext .ts,.tsx` — zero warnings; `npx vite build` — succeeds (same pre-existing >500kB chunk-size advisory as Sprint 18, not a new issue); `npm run verify:sqljs-parity` (Sprint 18's script, re-run unmodified) — **ALL SQL.JS PARITY CHECKS PASSED**, confirming the sync/devices wiring didn't disturb the underlying SQL layer.
- **Cross-platform consistency** (`app/backend/verification/sprint19_cross_platform_consistency_test.py`, run against this session's own sandboxed Postgres instance — same posture as Sprint 15's own scripts, not this project's real Supabase): two independent psycopg2 sessions standing in for mobile and web register/rename/revoke a device and cross-check visibility and RPC-guard rejection from the OTHER session. **8/8 checks passed**: registration visible cross-session immediately; rename issued by "web" visible to "mobile"; revoke issued by "mobile" visible to "web"; `getRegisteredDevices` (picker query) correctly excludes the revoked device while `getAllDevices` (panel query) still lists it as Revoked; `request_activation` is rejected for the revoked device from both sessions. Sandbox left in its pre-script state (fixture devices untouched, test device cleaned up).
- **Not verified this sprint, disclosed not hidden:** an actual browser run of the web sync client end-to-end against a real Supabase project (this sandbox has no browser environment or live Supabase project to drive) — same standing caveat as every Supabase-touching code path since Sprint 3, and the same one Sprint 18's own runbook already carried forward. `rename_device`/`revoke_device` were exercised directly via SQL in the cross-platform script (proving the RPCs' own logic), not through a live Supabase RPC call from a real `@supabase/supabase-js` client — the `SupabaseClientLike` typing fix (§4, Gotcha 1) is verified via `tsc`, not via a live call.

## 6. What is NOT covered this sprint (carried forward, by design)

- Live end-to-end verification against a real Supabase project and a real browser — owner-driven, same standing caveat as every prior sprint touching Supabase.
- A full "choose your own replacement device" picker UI for Revoke (§2) — the auto-selected default covers Vol 12_1 §8's own stated requirement.
- Per-device Supabase session invalidation on Revoke (§3) — a real, disclosed limitation of this app's one-Supabase-user-per-business auth model, not fixable without new session-tracking infrastructure this sprint didn't build.
- DEK rotation — unchanged top-priority open item, Vol 12_1 §12.
- PWA installability polish, photo/document capture, full settings editing — all unchanged carry-forwards from Sprint 18's own runbook, untouched this sprint.
